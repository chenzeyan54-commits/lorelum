## The agent cannot find `lore`

Run `lore --version` in the environment that starts the agent. If it works in your terminal but fails in the agent, check that the agent inherits `~/.local/bin` on `PATH`, then restart the application. See [Installation](./installation).

## A command fails

A normal CLI failure prints its code, message, recovery guidance, and `diagnostics.traceId` on stderr. That trace belongs to the original invocation, so copy it before retrying anything:

```sh
lore logs --trace-id <traceId> --limit 100
```

This reads only Lorelum-managed records already associated with that call. It does not start a Backend or model, download anything, rerun the query, or inspect another invocation. Treat `missingEvidence` as a limit on what was retained: a missing, rotated, damaged, or non-debug log is not proof of a different cause.

If the records do not explain the problem and you control a safe minimal reproduction, rerun that reproduction with `--debug`:

```sh
lore --debug query "the same minimal task description"
```

The reproduction has a new trace. Do not present its records as if they came from the original failure. Use `--json` only when you need protocol fields or a script needs the JSON envelope; do not rerun solely to obtain the original trace.

Host Hook stdout remains the host's raw protocol and does not include ordinary CLI diagnostics. Do not parse it for a trace. For a recurring Hook problem, enable `logging.level: debug` or reproduce the Hook through the host's supported path, then inspect the resulting local evidence deliberately.

## A query returns `preparing`

This is a successful response with exit code `1`: model preparation was accepted but is not ready within the CLI observation interval. Check its state and wait:

```sh
lore model status
lore model load
```

Retry the original query. If Lorelum reports a missing index, inspect and build it:

```sh
lore index status
lore index build
```

For `semantic.index-incompatible`, use `lore index rebuild` instead. An accepted build can still be running. Follow its operation ID with `lore index operation <operation-id>`. Use the same `--store-root` for Store-consuming commands. See [Index commands](./reference/indexing) for recovery errors.

## A query returns no matches

Run `lore pack list --details` and confirm the expected Pack is installed in this Store. Describe the task and decision rather than a broad topic; use `lore pack list <pack-name>` to browse Practices.

An empty result is different from `preparing` or an error. Agent integrations should inspect the JSON result before deciding what happened; see [CLI protocol](./cli).

## Model download fails

Check the reported `error.code`, available disk space, and network access to the configured model source. After fixing the cause, `lore model load` retries and waits. Model paths, cache locations, and download settings are described in [Embedding configuration](./configuration).

## Diagnose with keyword retrieval

For an intentional offline search or to isolate a model problem, use:

```sh
lore query "authentication token session" --mode keyword
```

Keyword search matches terms rather than meaning. Continue with the default natural-language query after resolving the semantic retrieval problem.

## Report a problem

First create a local, reviewable draft from the selected trace if it helps explain the problem:

```sh
lore feedback draft --trace-id <traceId> --kind bug
```

This only creates `report.json` and `report.md` below `~/.lorelum/feedback/`. It does not upload data, open a URL, or create an Issue. Add existing same-trace detail only when you intentionally choose `--include-logs info` or `--include-logs debug`, then review every field before sharing any part publicly.

If you decide to submit an Issue, include `lore --version`, your platform, the command, the returned error code, and only the reviewed evidence that helps maintainers reproduce it. Report security issues through [SECURITY.md](https://github.com/lorelum/lorelum/blob/main/SECURITY.md).
